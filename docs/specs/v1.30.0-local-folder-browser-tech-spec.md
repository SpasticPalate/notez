# Local Folder Browser — Technical Specification

**Target version:** v1.30.0
**Status:** Approved — ready for implementation planning
**Date:** 2026-09-09
**Scope:** Frontend only. No backend, database, or storage changes.

---

## 1. Problem

Notez users keep working material in local folders outside Notez — the driving case is a
user maintaining a "Cowork OS" folder of markdown files on her own machine. Today she must
switch to a separate editor to read or change those files, and there is no way to work with
them alongside her Notez notes.

She wants to open that folder from inside Notez, browse its structure, read the `.md` files
with proper formatting, edit them, and save changes back to disk. Viewing other common file
types found in the same folders (PDF, Word, Excel, plain text, images) is a desirable
extension.

## 2. The governing constraint

Notez runs as a container on a self-hosted server and is used through a browser. **The server
has no path to the user's disk.** The only component that can reach her files is her browser,
and only for files she explicitly grants access to.

This makes the feature almost entirely a frontend concern, which is the dominant fact in its
cost and its risk profile:

- No API routes, no Prisma migration, no MinIO involvement, no upload.
- File contents never reach the Notez server.
- Feature availability is bounded by browser capability, not by anything we control.

Two browser mechanisms exist:

| Mechanism | Capability | Support |
|---|---|---|
| File System Access API (`showDirectoryPicker`) | Persistent handle, live re-read, **write-back** | Chromium desktop only, requires secure context |
| `<input webkitdirectory>` | One-shot in-memory snapshot, re-pick each session, **read-only** | All browsers |

There is no polyfill for write access. Editing local files is achievable in Chromium and
nowhere else.

## 3. Goals

1. Open a local directory from Notez and browse its tree, including subdirectories.
2. Read `.md` files rendered with correct markdown formatting.
3. Edit `.md` files and save changes back to the original file on disk.
4. View `.txt` and other plain-text files.
5. View PDF, images (jpg/png/gif/webp/svg), `.docx`, and `.xlsx`.
6. Re-open a previously used folder with minimal friction on return visits.
7. Degrade honestly and legibly where the browser cannot support the full feature.

## 4. Non-goals

These are deliberate exclusions for v1.30.0, not oversights:

- **AI features on local files.** Summarize/suggest-tags would transmit the user's local
  document to a third-party model provider, breaching the boundary the rest of this feature
  respects. Revisit as an explicit, separately-consented decision.
- **Importing local files into Notez as notes.** Related to roadmap §3.3 (Import/Export) and
  tracked there. This feature is a window onto the filesystem, not an ingestion path.
- **Creating, renaming, moving, or deleting files and folders.** Editing existing file
  contents only.
- **Rich-text (WYSIWYG) editing of local markdown.** See §5 for rationale.
- **`.pptx` viewing.** No client-side library offers acceptable fidelity.
- **Mobile support.** No mobile browser exposes directory access.
- **Syncing, watching, or polling for external file changes.** Changes on disk are detected
  at save time (§6.5) and on manual refresh, not continuously.

## 5. Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Interaction model | Browse **and edit in place** | User requirement; files stay on disk as the source of truth |
| Browser strategy | Chromium-first full feature; read-only fallback elsewhere | Write access exists only in Chromium; a silent failure would be worse than a clear banner |
| Markdown editing | **Monaco source editor + live preview** | Byte-exact writes. A TipTap round-trip through HTML rewrites the entire file in turndown's style and risks mangling YAML frontmatter, `[[wikilinks]]`, callouts, footnotes and raw HTML |
| UI placement | **New top-level route `/files`** | Clean separation from Notez-owned content; room for a real tree; no change to `HomePage`/`EditorPage` layout |
| Save model | **Explicit save**, not autosave | Autosaving to a user's real files on their real disk is a materially different risk class from autosaving a database row |

## 6. Design

### 6.1 Module layout

```
frontend/src/
  lib/localFs/
    capability.ts       # detect: 'fsa' | 'webkitdirectory' | 'unsupported'
    handleStore.ts      # persist FileSystemDirectoryHandle in IndexedDB
    permissions.ts      # queryPermission / requestPermission, reconnect state
    tree.ts             # lazy directory listing, sorting, hidden-file filter
    resolve.ts          # resolve a relative path against a handle -> File -> blob URL
    types.ts            # LocalEntry, LocalFileRef, PermissionState
  pages/
    FilesPage.tsx       # route /files — tree pane + viewer pane
  components/localFiles/
    FileTree.tsx
    Breadcrumbs.tsx
    FileViewer.tsx      # dispatches via viewerRegistry
    ReconnectPrompt.tsx
    UnsupportedBrowserNotice.tsx
    viewerRegistry.ts   # extension -> lazy-loaded viewer component
    viewers/
      MarkdownViewer.tsx
      MarkdownEditor.tsx   # Monaco + preview
      TextViewer.tsx
      ImageViewer.tsx
      PdfViewer.tsx
      DocxViewer.tsx
      XlsxViewer.tsx
```

`viewerRegistry.ts` is the extensibility seam. Supporting a new file type is one registry
entry plus one component, touching nothing else.

### 6.2 Capability detection, permissions, and reconnect

`capability.ts` resolves one of three modes at route load by feature-detecting
`window.showDirectoryPicker` and a secure context.

Directory handles returned by `showDirectoryPicker({ mode: 'readwrite' })` are
structured-cloneable and are persisted in IndexedDB, keyed by a generated id, alongside the
folder's display name and last-opened timestamp. This drives a "Recent folders" list.

**The permission is not persisted with the handle.** On a return visit
`handle.queryPermission({ mode: 'readwrite' })` typically returns `'prompt'`, and
`requestPermission()` is only honoured inside a user gesture. The design therefore renders a
**"Reconnect to Cowork OS"** button rather than attempting an automatic prompt that would
silently fail.

Permission state machine:

| State | UI |
|---|---|
| `granted` | Tree renders immediately |
| `prompt` | Reconnect button; one click restores the folder and last-viewed file |
| `denied` | Explanatory message with a "Choose a different folder" action |

Chrome's persistence of these grants varies with browser configuration and installed-PWA
status. The design assumes the worst case — one reconnect click per session — and simply
benefits when the grant survives.

### 6.3 Tree

Directory entries are read **lazily, on expand**, never recursively upfront. A large vault
would otherwise stall the tab on open.

- Sort: directories before files, then case-insensitive name order.
- Hidden entries (leading `.`) and `node_modules` are filtered by default, with a toggle.
- The tree stores `FileSystemDirectoryHandle` / `FileSystemFileHandle` references, not paths;
  a display path is maintained separately for breadcrumbs.
- A manual refresh action re-reads the current directory.

### 6.4 Viewing and rendering

**Markdown.** `marked` to HTML, then **DOMPurify**, then render. Both are existing
dependencies. Sanitization is mandatory: a local `.md` file may legitimately contain
`<script>` or `<img onerror=...>`, and rendering it unsanitized would execute attacker- or
accident-authored script inside the user's authenticated Notez origin, with access to her
session. This is a real credential-exposure path, not a theoretical one.

**Relative assets.** Markdown of the form `![](./images/diagram.png)` must have its `src`
resolved against the containing directory handle, read to a `File`, and swapped for a blob
URL before render. Without this every embedded image in a real vault renders broken. Blob
URLs are revoked when the viewer unmounts or the file changes.

**Relative links** to sibling `.md` files navigate within the tree rather than performing a
browser navigation. Both this and `[[wikilink]]` resolution land in phase 5; until then such
links render as inert text rather than as broken navigation.

**Images** render via `<img src="blob:...">`. SVG is never inlined into the DOM — `<img>`
does not execute script inside SVG, inline `<svg>` does.

**PDF** renders in a sandboxed `<iframe>` pointed at a blob URL, using the browser's built-in
viewer.

**`.docx`** via `mammoth` to HTML, then DOMPurify. Complex layout, headers/footers and
tracked changes are lost; adequate for reading, not for pixel-accurate review.

**`.xlsx`** via SheetJS (npm package `xlsx`) to an HTML table, with a sheet selector.
Formulas render as computed values; charts, formatting and pivot tables are lost.

Both `mammoth` and SheetJS are `React.lazy`-loaded so they cost nothing in the main bundle
until such a file is opened.

**Plain text** (`.txt`, `.log`, `.json`, `.csv`, `.yml`, and common source extensions)
renders in Monaco with syntax highlighting where available. These types are read-only in
phase 1 and become editable in phase 2 on the same terms as markdown (§6.5), minus the
preview pane.

### 6.5 Editing and saving

Markdown files open in a split view: Monaco editing the raw source, rendered preview beside
it, with a toggle for source-only or preview-only.

- Writes are byte-exact. Only the user's actual edits change the file; frontmatter,
  wikilinks, and raw HTML pass through untouched.
- **Save is explicit** — `Ctrl/Cmd+S` and a Save button. A dirty indicator appears in the
  file tab.
- Leaving a dirty file triggers an in-app confirmation; leaving the page triggers
  `beforeunload`.
- Writing uses `handle.createWritable()`. By default this stages the write in a swap file and
  replaces the original on `close()`, so a failed or abandoned write does not truncate the
  file. Behaviour under cloud-sync clients (OneDrive, Dropbox) should be spot-checked during
  phase 2 rather than assumed.

**Conflict detection.** `file.lastModified` is captured when a file is opened. Immediately
before writing, the file is re-fetched via `handle.getFile()` and the timestamp compared. If
it has changed — because she edited it in Obsidian or VS Code meanwhile — a dialog offers:

| Action | Behaviour |
|---|---|
| Overwrite | Write the editor buffer, discarding the on-disk change |
| Reload | Discard the editor buffer, reload from disk |
| Save a copy | Write to `<name>.notez-copy.md` in the same directory, leaving both intact |

The file is never silently clobbered.

Editing is offered only for markdown and plain-text types. All other viewers are read-only.

### 6.6 Degraded modes

| Environment | Behaviour |
|---|---|
| Chromium desktop (Chrome, Edge) | Full: persistent handle, reconnect, live re-read, edit and save |
| Firefox / Safari desktop | Read-only via `<input webkitdirectory>`; folder re-picked each session; persistent banner explaining the limitation and why |
| Any mobile browser | Notice stating that a desktop Chromium browser is required; no picker offered |

The banner names the actual reason (the browser lacks the File System Access API) rather than
presenting a generic error.

## 7. Security considerations

1. **Sanitize all rendered file content.** Markdown and `.docx` HTML both pass through
   DOMPurify. This is the highest-severity item in the spec.
2. **No inline SVG.** Images render through `<img>` only.
3. **Sandbox the PDF iframe.**
4. **File contents and paths never leave the browser.** No API calls carry them, and no
   telemetry, error report, or OpenTelemetry span records file contents or absolute paths.
   Error reporting logs file extension and error class only.
5. **Revoke blob URLs** on unmount to avoid pinning file contents in memory.
6. **Scope is the picked directory.** The API grants access to that tree only; the
   application never attempts to traverse above it.

## 8. Testing

Vitest and Testing Library are already configured. `FileSystemDirectoryHandle` and
`FileSystemFileHandle` are plain objects, so a fake in-memory handle implementation makes
this properly testable without browser automation.

Required coverage:

- Tree construction, sort order, and hidden-file filtering.
- Lazy expansion reads only the expanded directory.
- Extension-to-viewer routing, including unknown extensions falling back to a
  "no preview available" state.
- **Markdown sanitization** — an explicit test asserting `<script>` and `onerror` attributes
  are stripped from rendered output.
- Relative image resolution produces a blob URL; unresolvable paths degrade gracefully.
- Permission state transitions: `granted`, `prompt`, `denied`.
- The dirty/save/conflict state machine, including all three conflict resolutions.
- Capability detection selecting the correct mode for each simulated environment.

## 9. Phasing

Each phase is a separate PR off `main` and is independently shippable.

| Phase | Scope | Estimate |
|---|---|---|
| 1 | Foundation: capability detection, picker, handle persistence, reconnect flow, lazy tree, breadcrumbs, markdown rendering with sanitization and relative-asset resolution, text viewer, `/files` route, read-only fallback and notices | 2 sessions |
| 2 | Editing for markdown and plain text: Monaco source + preview, dirty state, explicit save, conflict detection dialog, navigation guards | 1–1.5 sessions |
| 3 | Images and PDF viewers | 0.5 session |
| 4 | `.docx` (mammoth) and `.xlsx` (SheetJS), lazy-loaded | 1 session |
| 5 | Polish: filename filter, recent folders list, keyboard navigation, wikilink and relative-link navigation, dark mode pass, empty and error states | 1 session |

**Total: approximately 5.5–6 sessions**, where a session is a focused working block ending in
a reviewable PR. Phase 1 alone delivers the originally requested capability.

## 10. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Chrome permission persistence varies by configuration | Reconnect click may be needed every session | Design assumes the worst case; benefits silently when the grant persists |
| Large vaults slow the tree | Unusable on big folders | Lazy per-directory reads; measure against a realistically large vault in phase 1 |
| `.docx` / `.xlsx` fidelity is lossy | User may mistrust the rendering | Explicit "simplified preview" label on both viewers |
| Bundle growth from mammoth and SheetJS | Slower initial load for all users | `React.lazy` per viewer; verify with a build-size check in phase 4 |
| Feature is invisible or broken for non-Chromium users | Confusion, perceived breakage | Explicit capability banners naming the real reason |
